01한 줄 요약

  • 문제로그인 공급자(IdP)의 설정을 가져오지 못하면 TrafficPolicy 상태에 unexpected status code 503만 떠서, 공급자가 여러 개일 때 어느 쪽이 죽었는지 알 수 없었습니다.
  • 해결오류 메시지에 discovery URL을 넣되, URL 안의 비밀번호는 url.Redacted()로 가렸습니다. 기존 로그의 issuer_uri 필드에도 같은 마스킹을 적용했습니다.

02먼저 알아둘 개념

kgateway
Kubernetes용 API·AI 게이트웨이입니다. 사용자가 YAML로 정책을 쓰면 kgateway가 이를 Envoy 프록시 설정으로 번역합니다. 2018년 Solo.io의 Gloo로 시작한 CNCF 샌드박스 프로젝트이고, 스타는 5.7천 개입니다.
OIDC (OpenID Connect)
"구글로 로그인" 같은 로그인 표준입니다. 로그인을 대신 처리해 주는 곳을 IdP(Identity Provider)라고 부릅니다. Keycloak, Okta, Azure AD가 대표적입니다.
Issuer와 discovery
IdP 주소(issuer) 뒤에 /.well-known/openid-configuration을 붙여 요청하면, 토큰 발급 주소·로그인 주소·공개키 주소가 담긴 JSON을 받을 수 있습니다. 이 과정을 discovery라고 합니다. kgateway는 이 JSON으로 Envoy의 로그인 설정을 만듭니다.
GatewayExtension과 TrafficPolicy
GatewayExtension에 IdP 정보(issuerURI 등)를 적고, TrafficPolicy가 이를 참조해 특정 경로에 로그인을 붙입니다. GatewayExtension 하나를 여러 TrafficPolicy가 함께 참조할 수 있습니다.
Status condition
쿠버네티스 리소스의 status에 "적용됨/거절됨, 그 이유"를 적는 칸입니다. 문제가 생기면 운영자가 kubectl describe로 가장 먼저 보는 곳입니다.
캐시와 재시도
kgateway는 discovery 결과를 성공이든 실패든 캐시하고, 백그라운드에서 다시 시도합니다. 실패하면 30초부터 간격을 두 배씩 늘려 최대 5분까지 재시도합니다. 한 번 성공한 설정은 이후에 실패해도 계속 씁니다.

03무슨 문제였나

discovery가 실패하면 TrafficPolicy의 status에는 이런 메시지만 남았습니다.

error discovering OpenID provider config; unexpected status code 503

GatewayExtension이 하나뿐이면 괜찮습니다. 하지만 사내 Keycloak, Azure AD B2C, Okta처럼 IdP가 여러 개인 클러스터에서 하나가 503을 내면, status만 봐서는 어느 IdP가 죽었는지 알 수 없습니다. 결국 컨트롤러 로그를 뒤져 issuer_uri 필드를 찾아야 했습니다.

숨어 있던 두 번째 문제

그 로그의 issuer_uri는 사용자가 쓴 주소를 그대로 찍고 있었습니다. 주소에 https://client:secret@idp.example.com처럼 비밀번호가 들어 있으면, 그 비밀번호가 로그 수집 시스템까지 그대로 퍼집니다.

04이슈가 요구한 것

이슈 #14750은 쓰기 권한이 있는 COLLABORATOR(DuncanDoyle)가 올렸습니다. 고칠 위치를 줄 번호까지 짚고, 수정 방법과 완료 기준을 적어 둔 좋은 이슈였습니다.

  1. 상태에 URL 표시

    200이 아닌 응답과 해석할 수 없는 응답 본문, 두 가지 실패 모두 TrafficPolicy 상태에 discovery URL이 나와야 합니다.

  2. 비밀번호는 모든 곳에서 가림

    issuer URI 속 비밀번호는 로그와 상태 어디에서도 드러나면 안 됩니다. 기존 issuer_uri 로그 필드도 포함입니다.

  3. 통신 오류엔 URL 한 번만

    통신 자체가 실패한 오류에는 Go가 이미 URL을 넣어 주니, 거기에 또 덧붙이지 말아야 합니다.

이슈에는 열린 질문이 하나 있었습니다. 쿼리 문자열도 지울 것인가. 쿼리에는 진단에 쓸모 있는 정보가 들어 있을 수 있어서, 명시적으로 정하자고 했습니다.

05해결: 바꾼 코드

① URL을 가리는 헬퍼

pkg/kgateway/extensions2/plugins/trafficpolicy/oidc.go

// redactURL masks the password in rawURL's userinfo so the URL can be logged and surfaced in
// status. The query string is kept, since parameters such as Azure AD B2C's ?p=<policy> help
// tell which provider configuration failed.
func redactURL(rawURL string) string {
	u, err := url.Parse(rawURL)
	if err != nil {
		return "<invalid URL>"
	}
	return u.Redacted()
}

Go 표준 라이브러리의 url.URL.Redacted()는 비밀번호만 xxxxx로 바꾸고, 사용자 이름과 쿼리는 그대로 둡니다. 주소를 해석할 수 없을 때는 원문을 찍지 않고 <invalid URL>을 돌려줍니다.

② 오류 세 곳에 URL 넣기

URL 마스킹은 요청마다 할 필요가 없어서, 함수 시작에서 한 번만 계산합니다.

func (o *oidcProviderConfigDiscoverer) discover(ctx context.Context, discoveryURL string) (*oidcProviderConfig, error) {
+	redactedURL := redactURL(discoveryURL)
	...
	// 500·502·503·504: 재시도하는 실패
-	return fmt.Errorf("error discovering OpenID provider config; unexpected status code %d", resp.StatusCode)
+	return fmt.Errorf("error discovering OpenID provider config at %s; unexpected status code %d", redactedURL, resp.StatusCode)

	// 200인데 JSON을 해석하지 못함
-	return retry.Unrecoverable(fmt.Errorf("error decoding OpenID provider config: %w", err))
+	return retry.Unrecoverable(fmt.Errorf("error decoding OpenID provider config at %s: %w", redactedURL, err))

+	return retry.Unrecoverable(fmt.Errorf("error discovering OpenID provider config at %s; unexpected status code %d", redactedURL, resp.StatusCode))

③ 로그 두 곳 마스킹

-	logger.Warn("error refreshing OpenID provider config", "issuer_uri", issuerURI, ...)
+	logger.Warn("error refreshing OpenID provider config", "issuer_uri", redactURL(issuerURI), ...)

④ 일부러 건드리지 않은 곳

통신 자체가 실패할 때(client.Do 오류)는 Go의 HTTP 클라이언트가 이미 URL을 넣고 비밀번호도 ***로 가려줍니다. 여기에 URL을 또 붙이면 한 메시지에 URL이 두 번 나와서, 이슈의 세 번째 기준에 어긋납니다.

결과 비교

BEFORE

어느 IdP인지 모름

error discovering OpenID provider config; unexpected status code 503

AFTER

URL로 바로 식별

error discovering OpenID provider config at https://idp.example.com/.well-known/openid-configuration; unexpected status code 503

비밀번호가 가려지는 방식

어디서누가 가리나결과 예시
상태 코드·디코딩 오류 (이번 수정)url.URL.Redacted()http://client:xxxxx@idp.example.com/.well-known/openid-configuration
통신 실패 오류 (원래 동작)Go net/http 클라이언트http://client:***@idp.example.com/.well-known/openid-configuration
issuer_uri 로그 (이번 수정)redactURLhttp://client:xxxxx@idp.example.com
쿼리 문자열은 남겼다

Azure AD B2C는 ?p=<policy>처럼 쿼리로 어떤 로그인 정책인지 구분합니다. 쿼리를 지우면 같은 IdP 안에서 어느 정책이 실패했는지 알 수 없습니다. 그래서 비밀번호만 가리고 쿼리는 남기자고 선점 코멘트에서 먼저 제안했습니다. 메인테이너가 지우자고 하면 u.RawQuery = "" 한 줄만 추가하면 됩니다.

오류 메시지를 바꿔도 부작용이 없는 이유

kgateway는 이전 결과와 새 결과의 오류 문자열이 같은지 비교해서(sameOutcome), 다를 때만 설정을 다시 계산합니다. URL은 issuer마다 고정이라, 같은 실패가 반복되면 문자열도 똑같습니다. 그래서 불필요한 재계산이 생기지 않습니다.

09남은 이야기

재시도하면 URL이 여러 번 나온다

500·502·503·504는 최대 5번까지 재시도합니다. 재시도 라이브러리(retry-go)는 마지막 오류에 시도마다의 메시지를 모두 이어 붙이기 때문에, 5xx가 계속되면 status에 URL이 다섯 번 나옵니다. 실제 테스트 로그는 이랬습니다.

All attempts fail:
#1: error discovering OpenID provider config at http://127.0.0.1:65233/.well-known/openid-configuration; unexpected status code 503
#2: error discovering OpenID provider config at http://127.0.0.1:65233/.well-known/openid-configuration; unexpected status code 503
...
#5: error discovering OpenID provider config at http://127.0.0.1:65233/.well-known/openid-configuration; unexpected status code 503

retry.LastErrorOnly(true)를 쓰면 마지막 오류만 남길 수 있습니다. 하지만 캐시되는 오류 메시지 자체가 바뀌는 별도의 변경이라 이번 PR에서는 빼고, PR 설명의 Additional Notes에 적어 두었습니다.

메인테이너의 답을 기다리는 것

  • 쿼리 문자열을 남긴 결정에 대한 의견
  • CI 실행 승인과 코드 리뷰. 이 저장소의 외부 PR은 머지까지 중앙값 약 2.4일이 걸렸습니다.

10배운 점

  1. 좋은 이슈는 방법과 기준을 준다. 그대로 따르되, 열린 질문(쿼리)은 선점 코멘트에서 내 의견을 먼저 밝혔습니다.
  2. 오류 메시지는 운영자의 첫 단서다. "무엇이 실패했는지"와 함께 "어디서"를 알려줘야 합니다. 단, 비밀 정보는 가립니다.
  3. 메시지를 바꾸기 전에 그 문자열을 쓰는 곳을 찾는다. 이번에는 sameOutcome이 오류 문자열을 비교하고 있었습니다.
  4. 저장소의 규칙은 필수 검사다. DCO, PR 템플릿, labeler를 지키지 않으면 코드와 상관없이 CI에서 떨어집니다.
  5. 범위를 지킨다. 재시도 메시지 중복처럼 발견한 다른 문제는 고치지 않고 설명에 남겼습니다.

11스스로 설명해보기

면접에서 이 PR에 대해 나올 만한 질문입니다. 답을 펼치기 전에 먼저 말로 설명해 보세요.

왜 오류 메시지에 URL을 넣어야 했나요?

discovery 오류는 GatewayExtension을 참조하는 모든 TrafficPolicy의 status에 찍힙니다. IdP가 여러 개인 클러스터에서는 status만 보고 어느 IdP가 실패했는지 알 수 있어야, 운영자가 로그를 뒤지지 않고 바로 원인을 찾습니다.

비밀번호를 왜 가려야 하나요? 누가 이 메시지를 보나요?

status는 그 리소스를 읽을 권한이 있는 사람이면 누구나 볼 수 있고, 로그는 로그 수집 시스템을 통해 더 넓게 퍼집니다. issuer URI에 비밀번호가 들어 있으면 그대로 노출되니, 표시하는 모든 곳에서 가려야 합니다.

url.Redacted()는 무엇을 가리고 무엇을 남기나요?

비밀번호만 xxxxx로 바꾸고, 사용자 이름·호스트·경로·쿼리는 그대로 둡니다. 이슈에서 제안한 방식이 이 함수였고, 쿼리를 남기는 것도 의도한 동작입니다.

client.Do에서 나는 오류는 왜 그대로 뒀나요?

Go의 HTTP 클라이언트가 이미 *url.Error로 URL을 넣고, 비밀번호도 ***로 가려줍니다. 여기에 URL을 또 붙이면 한 메시지에 두 번 나옵니다. 이슈의 "통신 실패에는 URL을 정확히 한 번" 기준에 맞추려고 건드리지 않았고, 이 동작은 통신 실패 테스트로 직접 확인했습니다.

오류 문자열을 바꾸면 KRT 재계산이 늘어나지 않나요?

kgateway는 이전 결과와 새 결과의 오류 문자열이 같은지 비교해 다를 때만 다시 계산합니다(sameOutcome). URL은 issuer마다 고정이라 같은 실패가 반복되면 문자열도 같습니다. 그래서 재계산이 늘지 않습니다. 이슈 작성자도 같은 점을 짚었습니다.

쿼리 문자열을 남긴 이유는요? 반대 의견은 없을까요?

Azure AD B2C는 ?p=<policy>로 로그인 정책을 구분해서, 쿼리가 있어야 어느 정책이 실패했는지 알 수 있습니다. 반대로 어떤 IdP는 쿼리에 민감한 값을 넣을 수도 있습니다. 그래서 혼자 정하지 않고 선점 코멘트로 먼저 의견을 물었고, 지우자는 답이 오면 한 줄로 바꿀 수 있게 해 두었습니다.

통신 실패는 테스트에서 어떻게 만들었나요?

httptest 서버를 띄워 주소를 얻은 뒤 곧바로 닫았습니다. 그 주소로 요청하면 연결이 거부됩니다. 재시도가 5번 일어나서 이 케이스만 1.5초쯤 걸립니다.

5xx 오류에서 URL이 여러 번 나오는 건 왜 고치지 않았나요?

retry-go가 시도마다의 오류를 모두 이어 붙이기 때문입니다. retry.LastErrorOnly(true)로 줄일 수 있지만, 캐시되는 오류 메시지가 바뀌는 별도의 결정입니다. 이슈 범위를 넘어서서 PR 설명에 적어 메인테이너가 판단하게 했습니다.
